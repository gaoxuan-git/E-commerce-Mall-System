# 开发环境一号通全量模拟设计

## 背景

管理后台订单发货选择“电子面单打印”后，会请求
`GET /api/admin/express/template`。当前实现通过一号通获取面单模板，
本地没有配置 `access_key` 和 `secret_key`，因此返回
“请配置一号通 应用对应的 accessKey”。

一号通还被短信、物流查询、快递公司同步、电子面单打印、商家寄件和
商品采集共同使用。只修复当前模板接口会让其他本地流程继续依赖真实
第三方服务。

## 目标

- 在 Spring `dev` Profile 下模拟所有一号通能力。
- 开发环境不要求配置一号通密钥，不请求 `sms.crmeb.net`。
- 返回满足现有前后端契约的稳定假数据，使相关功能可以完成本地验收。
- 开发模式下移除后台可见的一号通品牌、登录、注册和开通提示。
- 保留短信、物流、电子面单、商家寄件和商品采集等业务功能入口。
- 生产及其他非 `dev` 环境继续使用现有真实一号通逻辑。

## 非目标

- 不删除生产环境的一号通实现。
- 不接入新的短信、物流或面单供应商。
- 不把开发假数据做成后台可编辑功能。
- 不保证开发模拟结果可用于真实寄件、真实打印或真实物流追踪。

## 方案比较

### 方案 A：统一出口模拟

将所有一号通外部请求统一收口到 `OnePassUtil`。开发环境由专用响应
工厂根据已知 API 路径返回固定契约；生产环境继续通过
`RestTemplateUtil` 请求真实服务。

优点：

- 可以在一个边界保证开发环境绝不访问一号通。
- 复用现有业务解析和页面交互逻辑。
- 生产路径改动小。
- 新增一号通接口时可以明确要求补充模拟契约。

这是本次采用的方案。

### 方案 B：各业务服务分别增加开发分支

短信、物流、面单、寄件和商品采集分别判断开发开关并构造假数据。
数据含义直观，但分支分散，容易遗漏调用或出现不一致。

### 方案 C：写入假密钥

在数据库中写入假的 `access_key` 和 `secret_key`。该方案仍会请求真实
一号通并在登录阶段失败，不能满足“不使用一号通”的要求。

## 配置与启用条件

在管理端和前台的 `application-dev.yml` 中增加：

```yaml
crmeb:
  one-pass:
    dev-mock:
      enabled: true
```

开发模拟只有在以下条件同时满足时启用：

1. 当前 Spring Profile 包含 `dev`。
2. `crmeb.one-pass.dev-mock.enabled=true`。

任一条件不满足时，所有调用继续执行原生产逻辑。其他环境配置文件不
增加启用开关。

## 架构

### 统一外部请求边界

`OnePassUtil` 负责判断是否启用开发模拟：

- 模拟开启时，登录对象和 Token 使用固定本地值，不读取系统密钥，
  不访问 Redis Token 缓存。
- `postFrom`、`getFrom` 和 `getData` 将请求交给开发响应工厂。
- 模拟关闭时，保持现有密钥读取、Token 缓存和 HTTP 请求逻辑。

`SmsServiceImpl` 当前有两处直接调用 `RestTemplateUtil` 发送一号通
短信。它们改为通过 `OnePassUtil` 请求，确保不存在绕过统一边界的
外部调用。

### 开发响应工厂

响应工厂只识别项目当前使用的固定 API 路径，并返回与真实接口相同的
顶层结构。所有响应均使用确定性数据，便于测试。

如果开发环境调用了未覆盖的一号通路径，响应工厂直接抛出
“开发模拟未实现该接口”，不得回退到真实网络。

## 模拟行为

### 账号与服务状态

- 返回本地模拟账号，不读取 `access_key` 或 `secret_key`。
- 短信、物流、电子面单和商品采集服务均返回已开通状态。
- 套餐余量返回固定充足数值，页面不会出现充值或开通阻断。
- 登录、修改密码、修改手机号和服务开通返回模拟成功。

### 短信

- 验证码继续使用现有开发固定码 `123456`。
- 通知短信和后台短信发送只记录带 `[DEV MOCK]` 标记的脱敏日志并
  返回成功。
- 短信模板和申请记录返回固定列表。
- 不记录验证码或完整手机号。

### 快递公司与电子面单

- 快递公司同步返回本地固定快递公司列表。
- 面单模板查询按快递公司返回固定模板，包含可供页面选择的数据。
- 电子面单打印生成本地测试面单号和测试标签。
- 测试标签明确标记为非真实面单，不依赖第三方图片地址。

### 商家寄件

- 快递列表返回固定公司、业务类型和面单模板。
- 创建寄件返回本地任务号、订单号和测试运单号。
- 因开发环境不会收到第三方回调，创建成功后立即按现有订单规则推进
  为已发货，并写入订单状态记录。
- 取消寄件返回成功并按现有取消逻辑清理模拟寄件数据。

### 物流查询

- 返回固定物流轨迹和已签收状态。
- 运单号、快递公司等字段沿用当前请求数据，避免订单详情错配。
- 结果可以使用现有 Redis 缓存逻辑。

### 商品采集

- 返回一件结构完整的固定测试商品，包含基础信息、价格、库存、图片、
  规格和属性值。
- 商品名称和详情明确标记为开发模拟数据。
- 不解析用户提交的真实外部商品页面，也不请求第三方地址。

## 管理后台

开发构建下：

- 短信配置页显示“本地模拟短信服务”，不加载一号通 iframe。
- 隐藏一号通账号注册、登录和服务开通引导。
- 商品采集配置使用“平台采集”或“本地模拟采集”等中性名称。
- 订单发货继续显示“电子面单打印”和“商家寄件”等业务名称。
- 不显示一号通未配置、密钥配置或套餐购买提示。

生产构建保留现有一号通页面和文案。

## 数据流

```text
业务服务
  -> OnePassUtil
     -> dev Profile + dev-mock=true
        -> 开发响应工厂
        -> 返回固定契约
     -> 其他情况
        -> 读取真实密钥和 Token
        -> RestTemplateUtil
        -> 一号通
```

商家寄件额外执行本地状态推进：

```text
后台提交商家寄件
  -> 返回模拟任务号和运单号
  -> 保存寄件信息
  -> 立即执行已揽件等价逻辑
  -> 订单进入已发货
```

## 错误处理与日志

- 未覆盖的模拟接口直接失败，不访问真实网络。
- 假数据结构缺失时按现有业务错误返回，不静默吞掉异常。
- 模拟日志统一使用 `[DEV MOCK]`，便于验收时检索。
- 手机号、收件地址、密钥和 Token 不写入模拟日志。
- 非 `dev` 环境不识别模拟账号或模拟 Token。

## 测试

### 单元测试

- `dev` 且开关开启时，获取登录对象和 Token 不读取系统密钥。
- 开关关闭或非 `dev` Profile 时，不进入模拟分支。
- 所有已知 API 路径返回现有业务代码可解析的结构。
- 未知 API 路径明确失败，且不调用 `RestTemplateUtil`。
- 短信发送统一经过 `OnePassUtil`，模拟模式不发起 HTTP 请求。
- 面单模板、打印、寄件、物流和商品采集返回稳定假数据。
- 模拟商家寄件会把订单推进为已发货。

### 集成与回归测试

- 后台选择不同快递公司时可以加载电子面单模板，不出现密钥提示。
- 使用电子面单打印发货可以生成测试运单号和标签。
- 使用商家寄件发货后，订单直接进入已发货。
- 查询订单物流可以看到固定轨迹。
- 短信验证码、通知短信和商品采集流程可以完成。
- 管理后台开发构建不显示一号通品牌、登录和开通提示。
- 运行受影响模块测试及现有订单发货端到端用例。
- 检查运行日志，确认不存在 `sms.crmeb.net` 请求和
  “请配置一号通”错误。

## 回退

将开发配置中的 `crmeb.one-pass.dev-mock.enabled` 改为 `false` 即可
恢复现有一号通逻辑。生产环境无需修改配置或数据库。
